# M11 — #12: why a dataviewjs view's output is missing from some exported pages

**Build:** the release `1.10.0` (`main.js` `e64a7a36…`), unchanged. The
instrument is in the vault, not in the plugin: the author's statblock view
(a `dv.view` script used by about 40 notes) replaced by a diagnostic copy,
version `issue12-diag.1`, that behaves and draws exactly as the original and
appends one JSON line per step to
`~/Downloads/roa-export-diag/2026-11-11-issue12/view-log.jsonl`.
**Runs in:** the author's working vault `Raiders of Arismyth Rules`, exporting
with the "Online website" preset to the usual export folder.
**Purpose:** G0 measurement for #12, before any story (SCAR-045: the failure
is seen only on the desktop). It decides between two explanations, both
unverified (SCAR-024):

- **A — copied early:** the off-screen render's wait ends when no
  `block-language-*` element is empty (`render-api.ts`, `renderDetached`);
  `dv.view` puts the view's CSS into the block before its script runs, so the
  block may count as filled while the script has not drawn yet.
- **B — no page yet:** `dv.current()` returns nothing for the note in the
  off-screen render (Dataview's index not ready), and the view returns
  without drawing.

The log tells them apart: a note missing from the export whose log shows the
view's `root` step or later in the export's render is A; one whose log shows
`current` with `page: false` is B.

## Result (2026-11-11, run by the author)

Instrument checked first (step 2: lines with `issue12-diag.1`, `host: view`).
Run 1 without clearing the cache is **void**: all 38 entry pages
byte-identical to the previous export, no line from the export's render —
the plugin re-used its cached pages. Runs 2 to 4 with the cache cleared,
each 39 renders of the view in the export (38 entry notes, one of them also
embedded in another note):

| Run | Views lost | Views whose container was detached when the script started | Block held only the CSS at script start | `dv.current()` empty | Errors |
|-----|-----------|------------------------------|----|----|----|
| 2 | 3 | the same 3 | 39/39 | 0 | 0 |
| 3 | 2 | the same 2 | 39/39 | 0 | 0 |
| 4 | 2 | the same 2 | 39/39 | 0 | 0 |

- Every lost view ran to its last step (`done`) — after the page had been
  copied and its host removed. **Explanation A is measured** (scope: this
  vault, one `dv.view` script, release 1.10.0 on the desktop, three runs):
  the wait in `renderDetached` ends while the block holds only the view's
  CSS, and the copy can happen before the script has started.
  **Explanation B is not supported** (0 of 117 renders without a page).
- Which notes are hit varies per run; the embedded copy was hit in all three
  runs and in the export of 2026-11-10 22:21.
- In run 2 (not counted for runs 3 and 4), three further views were
  detached only at their last step (after drawing):
  their output was exported; it shows that the copy happens at any point of
  the script, not only before it.
- Upstream 1.9.2's export of 2026-11-09 lost one of the same views.
- Not explained: each entry note was also rendered twice outside the
  export's off-screen host during each export (76 `host: view` renders per run).
- The original view is restored and verified (`shasum -c before.sha256`: OK).
